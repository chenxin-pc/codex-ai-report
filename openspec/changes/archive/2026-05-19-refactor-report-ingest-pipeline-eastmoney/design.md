## Context

当前离线分析流程以 `pipeline.py` 为主，但该文件已包含采集、下载、上传、SQL 查询、Excel 生成、搜索评估、命令解析与状态管理等多种职责，维护成本持续上升。项目已明确后续不再兼容旧批处理模板，目标改为保留东方财富拉取能力，并确保拉取后的导入、质量导出、评估链路持续稳定。

## Goals / Non-Goals

**Goals:**
- 将导入分析脚本收敛到单入口 `pipeline.py`，移除旧兼容脚本。
- 为导入输入增加东方财富来源模式，并复用既有导入 API 与状态模型。
- 按职责拆分 `pipeline.py`，降低耦合并提高测试覆盖的可维护性。
- 保证质量导出与搜索评估能力在重构后行为一致，满足现有规格要求。

**Non-Goals:**
- 不修改在线 Spring 导入主链路与推荐主链路接口契约。
- 不在本次变更中实现复杂反爬、登录态管理或浏览器自动化采集平台。
- 不新增必须依赖的新基础设施（如消息队列、任务编排平台）。

## Decisions

### 1. 单入口 + 模块化拆分

保留 `commands/pipeline.py` 作为唯一 CLI 入口，仅负责参数解析与阶段编排；将采集、上传、状态、查询、导出、评估等实现拆到独立模块。

备选方案：继续在单文件内增量维护。  
不采用原因：新增东方财富采集后复杂度会继续堆积，测试和回归成本更高。

### 2. 东方财富作为输入模式接入现有 ingest 流程

在输入采集层新增 `eastmoney` 模式，产出统一 `ReportInput` 结构，后续复用现有 `ingest_reports`、`RunState`、`export-quality`、`evaluate-search` 流程。

备选方案：单独增加“东方财富专用流水线脚本”。  
不采用原因：会再次形成双轨维护，与“单入口收敛”目标冲突。

### 3. 删除旧兼容脚本，明确 BREAKING 变更

移除 `import_reports_and_export_chunks.py` 及其在 README 的使用说明，避免使用方继续依赖旧参数和旧三 sheet 模板；统一迁移到 `pipeline.py` 命令体系。

备选方案：保留旧脚本并内部代理到新逻辑。  
不采用原因：需求已明确无需兼容旧模板，保留代理会增加长期维护负担。

### 4. 先抽公共能力，再迁移命令逻辑

优先抽取共享模块（如 `mysql_client`、`xlsx_writer`、`text_utils`），再迁移输入采集与导出逻辑，最后在 `pipeline.py` 收敛编排，降低一步到位重构风险。

备选方案：一次性整体迁移。  
不采用原因：风险高、难以定位回归来源。

## Risks / Trade-offs

- [Risk] 删除旧脚本导致已有命令调用失败 -> Mitigation：在 README 与变更说明中提供一对一替代命令映射，并补充迁移说明。
- [Risk] 模块拆分过程中行为漂移 -> Mitigation：补充脚本级测试，覆盖输入采集、导入状态、质量导出结构与关键异常路径。
- [Risk] 东方财富来源不稳定导致采集失败 -> Mitigation：采集阶段记录失败状态与错误摘要，遵循 continue/stop 策略，不阻断整体可观测性。
- [Risk] 重构影响性能或执行时长 -> Mitigation：保持现有导入与查询策略，避免引入额外网络往返和重复查询。

## Migration Plan

1. 新增模块目录并迁移公共函数，保持 `pipeline.py` 对外命令不变。
2. 将现有本地目录/URL 清单采集逻辑迁移到输入模块，并新增东方财富采集模式。
3. 迁移质量查询与 Excel 生成逻辑到独立模块，确保 `export-quality` 输出结构不变。
4. 删除旧兼容脚本及 README 旧路径说明，补充统一命令用法。
5. 完成脚本级测试回归与必要的 `mvn -q test`、`openspec validate --all --strict` 校验。

## Open Questions

- 东方财富第一版拉取是“固定 URL 清单接口”还是“页面自动发现 + 下载”。
- 东方财富元数据字段最小集合是否包含机构、发布日期、标题标准化规则。
- 东方财富拉取失败时，默认是否继续处理其他候选报告（沿用 `runtime.continue_on_error` 或单独配置）。
