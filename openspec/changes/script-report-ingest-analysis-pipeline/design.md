## Context

当前系统已有在线导入和推荐接口，核心链路由 Spring Boot Service 负责 OCR、语义切片、MySQL 入库、Milvus 向量化和推荐生成。批量收集网站研报、每次导入 10 篇、导入后从数据库拉取 OCR/切片/搜索数据做分析，更接近离线评估工作流。如果把这些流程全部内置到在线业务代码中，会让 Controller/Service 承担批处理、文件导出、外部网站采集和评估编排职责，增加主链路复杂度。

本设计采用脚本化流水线：脚本负责收集输入、批量调用现有导入能力、导入完成后查询数据库和接口、生成 Excel；业务代码只补齐脚本需要的稳定数据和必要的查询能力。这样既能快速迭代评估流程，也能保持在线应用职责清晰。

## Goals / Non-Goals

**Goals:**

- 提供可重复执行的脚本，一次收集并导入 10 篇研报。
- 支持从网站下载研报或从本地目录读取研报，采集来源通过配置控制。
- 脚本调用现有导入 API 或受控服务入口完成 OCR、切片、MySQL 入库和 Milvus 向量化。
- 导入结束后，脚本从数据库拉取报告、OCR、chunk、过滤诊断和搜索评估数据并生成 Excel。
- 脚本按配置 query 集合执行搜索评估，并整理 query 输入、召回输出、推荐结果和人工评价字段。
- 脚本运行参数、数据库连接、API 地址、输出目录和评估 query 均可配置，且不得硬编码密钥。
- 脚本失败时保留运行日志、失败清单和可重试状态。

**Non-Goals:**

- 不把“每 10 篇自动导出 Excel”的批处理规则写入在线 Controller。
- 不在本次变更中实现复杂网站爬虫平台、反爬绕过或登录态管理。
- 不替代核心 OCR、切片、Milvus 检索和推荐算法优化；脚本只编排和分析这些能力。
- 不要求脚本直接访问 Milvus 进行向量写入；向量化仍由后端导入能力负责。

## Decisions

### 1. 脚本作为离线编排入口

新增 `scripts` 或项目约定目录下的命令行脚本，负责 `collect -> ingest -> evaluate -> export` 四段流程。脚本可以通过 Maven/Java CLI 或轻量 shell 包装启动，但核心逻辑优先复用 Java 代码和项目配置，避免在 shell 中堆复杂业务逻辑。

替代方案是把批处理写成在线接口。该方案调用方便，但会污染业务主链路，并引入长耗时请求、文件输出和外部网站访问等问题，因此不采用。

### 2. 导入优先调用现有后端 API

脚本导入研报时优先调用现有上传接口，确保 OCR、切片、入库和向量化路径与线上行为一致。只有当 API 缺少必要返回字段时，才补充受控查询接口或从数据库读取结果。

替代方案是脚本直接调用 Service 或 Mapper。该方案执行效率高，但更容易绕过接口校验和事务边界，也不利于在独立环境运行，因此不作为首选。

### 3. 采集来源配置化，先支持本地目录和简单 URL 清单

第一阶段脚本支持两类输入：本地 PDF 目录、URL 清单文件。网站页面自动发现可以预留扩展点，但不承诺处理复杂反爬、登录或动态渲染。每个采集文件需要记录来源 URL、本地路径、标题、机构、发布日期和下载状态。

替代方案是一次性实现完整网站采集器。该方案范围过大，会把重点从 OCR/切片/搜索质量评估转移到采集稳定性，因此先不采用。

### 4. 导出从数据库和接口拉取分析数据

脚本导入完成后，从 MySQL 拉取报告元数据、OCR 页级结果、chunk、过滤诊断和搜索评估记录。搜索评估可以通过推荐 API 执行，也可以调用专门的评估入口；最终 Excel 由脚本生成，在线服务只需保证数据可追溯。

替代方案是导入过程中在线服务直接生成 Excel。该方案自动化程度高，但会让导入主流程承担导出失败、文件路径、重跑等非核心职责，因此本次改为脚本导出。

### 5. 脚本运行结果必须可重试

每次脚本运行生成 runId，记录输入清单、成功导入报告、失败文件、错误摘要、导出文件路径和搜索评估状态。重复执行时，脚本必须能跳过已成功导入的文件或按参数强制重跑，避免重复污染数据库和向量库。

替代方案是脚本只打印日志不留状态。该方案简单，但失败后很难恢复，也难以追溯 Excel 对应的输入批次，因此不采用。

## Risks / Trade-offs

- [Risk] 网站采集不稳定或触发访问限制 -> Mitigation: 第一阶段支持 URL 清单和本地目录，网站自动发现作为扩展能力。
- [Risk] 脚本重复运行导致重复导入 -> Mitigation: 使用文件指纹、来源 URL 或报告元数据做幂等检查，并提供显式强制重跑参数。
- [Risk] 脚本直接读取数据库导致与在线模型耦合 -> Mitigation: SQL 查询集中在脚本数据访问层，字段变更同步测试；必要时补充稳定查询接口。
- [Risk] 长文本 Excel 文件过大 -> Mitigation: 提供摘要列和完整文本列，必要时限制单元格长度并保留数据库主键追溯。
- [Risk] 配置泄露密钥 -> Mitigation: 配置样例只使用环境变量占位符，日志和 Excel 禁止输出 API Key、Token、数据库密码。
- [Risk] 脚本执行耗时过长 -> Mitigation: 每个阶段输出进度和状态文件，失败后可从上次成功阶段继续。

## Migration Plan

1. 新增脚本目录、配置样例和运行说明，不改变现有上传/推荐 API 行为。
2. 如果脚本需要的数据当前未持久化，先补充 OCR、chunk 诊断、搜索评估相关表和 Mapper。
3. 在测试环境用本地目录模式跑通 10 篇研报导入、搜索评估和 Excel 导出。
4. 再启用 URL 清单模式，验证下载、导入幂等和失败重试。
5. 生产使用前将真实网站来源、数据库连接、API 地址和输出目录改为环境变量或外部配置。
6. 如需回滚，停止使用脚本即可，不影响在线导入和推荐主链路。

## Open Questions

- 脚本第一版采用 Java CLI、Maven task，还是 shell 包装 Java 命令？
- 网站研报来源是否已经有固定 URL 清单，还是需要页面自动发现？
- 重复导入的幂等键优先使用文件 SHA-256、来源 URL，还是标题+机构+发布日期？
- Excel 输出是否只保存在本地目录，还是需要后续上传到对象存储或共享盘？
