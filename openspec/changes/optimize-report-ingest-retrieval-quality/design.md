## Context

当前研报导入主链路为 `MultipartFile -> OCR -> LLM 语义边界规划 -> PARENT/CHILD chunk -> MySQL -> Milvus CHILD 向量入库`，搜索链路为 `query -> Milvus ANN topK -> PARENT 上下文扩展 -> Qwen 推荐生成`。现有实现已经遵循 Controller 简洁、Service 编排、Prompt 文件化、MyBatis XML、Milvus ANN、Qwen embedding 配置化等项目规则，但核心质量问题缺少足够可追溯数据：OCR 原文、清洗前后差异、切片边界、过滤原因、召回分数和推荐证据组织没有稳定沉淀。

本次设计只处理在线核心能力：OCR 质量数据沉淀、语义切片质量优化、Milvus 检索质量优化和推荐证据约束。批量采集 10 篇研报、导入后从数据库拉取数据、Excel 导出和离线搜索评估由 `script-report-ingest-analysis-pipeline` 负责，本变更只保证脚本能查到足够可信的数据。

## Goals / Non-Goals

**Goals:**

- 保留页级 OCR 结果、清洗后文本、诊断信息和异常原因。
- 保留段落 atom、LLM 切片边界、边界修复结果、PARENT/CHILD chunk、token 数、页码范围和过滤原因。
- 优化 Milvus ANN 初召回和推荐证据组织，使最终建议更严格地基于高相似度证据。
- 提供脚本后续分析所需的稳定数据库数据和必要查询能力。
- 所有表结构变更同步 `schema.sql`，所有 SQL 继续放在 MyBatis XML 中。
- 行为变更提供针对性单元测试，测试不依赖真实 OCR、Qwen 或 Milvus 服务。

**Non-Goals:**

- 不在本变更中实现“每导入 10 篇自动导出 Excel”。
- 不在在线导入完成后自动执行搜索评估。
- 不实现 Excel 生成、文件输出目录管理或人工评价表单。
- 不在本次变更中引入真实证券交易决策或自动下单能力。
- 不承诺一次性接入专用商业 rerank 模型；本次仅预留重排策略接口并可先实现轻量级重排。
- 不改变 “LLM 只规划语义边界，不改写 OCR 原文生成 chunk 正文” 的原则。
- 不把完整 Prompt、OCR 原文或用户敏感信息输出到日志。

## Decisions

### 1. 核心服务只沉淀质量数据，不编排批量导出

在线服务负责在导入和检索过程中沉淀可分析数据，例如 OCR 页级结果、清洗诊断、段落 atom、切片边界、过滤原因和检索 metadata。批量导入、搜索评估和 Excel 导出交给脚本读取这些数据后完成。

替代方案是在导入主流程里每满 10 篇自动导出 Excel。该方案自动化程度高，但会让在线主链路承担批处理、文件输出和失败重试职责，因此移出本变更。

### 2. 保留页级 OCR 和段落级 atom

OCR 客户端继续位于 `common.ocr`，识别结果扩展为页级文本和诊断字段。Service 层新增 OCR 清洗/规范化组件，将原始 OCR 转为段落 atom，并保留 `pageNumber`、`paragraphId`、`sectionPath`、清洗标记和噪声诊断。切片服务基于 atom 请求 LLM 规划边界。

替代方案是只保存清洗后的全文。该方案持久化简单，但无法定位 OCR 页面问题，也无法让脚本解释切片为何失败，因此不采用。

### 3. PARENT 用于上下文，CHILD 用于向量检索

继续只将 CHILD chunk 写入 Milvus，PARENT chunk 存储在 MySQL 用于推荐证据扩展。CHILD chunk 的目标长度应更适合 embedding 语义匹配，PARENT chunk 保留完整论证上下文。chunk metadata 必须包含 report、chunk、parent、section、token、页码范围等字段。

替代方案是同时将 PARENT 和 CHILD 入库检索。该方案可能提升召回，但容易让大块 PARENT 稀释向量语义，并增加去重成本。本次优先保持 CHILD ANN，后续可通过脚本评估数据决定是否扩展。

### 4. 抽取共享检索组件供推荐和脚本评估复用

新增检索组件承载 query 规范化、Milvus ANN 初召回、结果去重、上下文扩展和可选重排。在线推荐接口直接调用该组件；脚本化搜索评估可以调用推荐接口或后续受控评估入口，确保评估路径与真实检索逻辑一致。

替代方案是在脚本中单独实现搜索逻辑。该方案短期简单，但会导致脚本评估结果不能代表真实推荐质量，因此核心检索逻辑仍放在服务端可复用组件中。

### 5. 失败必须显式暴露并保留诊断

OCR 空文本、LLM 切片无有效边界、边界修复后仍不连续、Milvus 未配置等情况必须显式失败或记录可诊断状态。对于导入主事务，MySQL 和 Milvus 的一致性需要通过事务边界、失败顺序和补偿任务评估；不能把失败静默伪装成成功。

替代方案是遇到异常时尽量返回部分结果。该方案对用户体验看似友好，但会污染向量库和后续脚本分析数据，因此不作为主路径。

## Risks / Trade-offs

- OCR 质量依赖外部服务和 PDF 渲染质量 -> 将 DPI、模型、任务类型做成配置，并沉淀页级诊断，便于脚本对比实验。
- 脚本需要的数据字段可能增加数据库体积 -> 对长文本和诊断字段进行合理分表或字段约束，并通过主键追溯。
- topK 扩大和重排会增加 Milvus/LLM 成本 -> 初召回 topK、最终 topK、重排开关和缓存 TTL 配置化，默认采用保守值。
- 导入事务与 Milvus 写入不完全同事务 -> 保留失败诊断，后续可增加重试或补偿清理。
- 脚本化评估与在线推荐仍可能出现版本差异 -> 脚本优先调用在线推荐接口或共享服务入口，避免复制检索逻辑。

## Migration Plan

1. 新增配置、实体、Mapper XML 和 schema，保持现有上传/推荐 API 可用。
2. 新增 OCR、段落 atom、chunk 诊断和过滤原因持久化时，默认从新数据开始；历史数据需要分析时由脚本补跑导入或单独迁移。
3. 部署后先在测试 profile 下使用 mock OCR/Qwen/Milvus 或隔离环境验证导入和检索质量数据沉淀。
4. 再由 `script-report-ingest-analysis-pipeline` 读取这些数据生成 Excel 和执行离线评估。
5. 回滚时关闭新增质量诊断持久化或回退查询入口，保留原上传与推荐主链路。

## Open Questions

- 段落 atom 和 OCR 页级结果是否需要独立表，还是作为 JSON 诊断字段存储？
- 搜索重排第一阶段采用规则分数融合，还是使用 Qwen 进行轻量重排？
- 检索组件是否需要提供内部评估入口给脚本调用，还是脚本只调用公开推荐 API？
